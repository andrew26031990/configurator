## Миграции базы данных

Схема базы ведётся через собственный CLI-раннер `bin/migrate.php` (без
composer и фреймворков). Миграции лежат в `migrations/` — PHP-файлы с
`up()`/`down()`, применяются по порядку имени (префикс-таймстамп). Раннер
хранит применённые версии в таблице `schema_migrations` и работает **только
из командной строки**.

**Когда запускать при выкладке:** после того как код выложен (шаг 3) и
`config.local.php` на сервере создан (шаг 2) — раннер берёт подключение к БД
оттуда. Запускать из корня проекта.

```bash
php bin/migrate.php status
```
```bash
php bin/migrate.php up
```

Команды: `status` (что применено / что ожидает), `up [N]` (накатить все или N),
`down [N]` (откатить последнюю или N), `create "имя"` (создать новый файл
миграции), `baseline <версия>` (пометить миграцию применённой без выполнения —
escape-hatch, обычно не нужен).

**Как `up` ведёт себя на боевой базе:**

- `00000000_000000_baseline` — исполняет `schema/baseline.sql` (снимок
  `mysqldump --no-data` с `CREATE TABLE IF NOT EXISTS`). На существующей базе
  это **no-op**: все легаси-таблицы уже есть, миграция просто помечается
  применённой. На чистой базе — создаёт всю структуру. Откат baseline
  запрещён (снёс бы всю схему).
- `..._create_rbac_tables` — создаёт `roles`, `permissions`,
  `role_permissions`, `user_roles` (InnoDB, FK `ON DELETE CASCADE`) и колонку
  `users.is_active`.
- `..._seed_rbac` — наполняет роли (superadmin/manager/editor/viewer), каталог
  прав и их маппинг, и выдаёт **всем существующим пользователям роль
  `superadmin`** (чтобы никого не залочить). Понизить роли — потом через
  админку «Пользователи».

**Требования и подводные камни:**

- БД-пользователь должен иметь права DDL (CREATE/ALTER/FOREIGN KEY). Если нет —
  миграция упадёт с понятной ошибкой, нужен доступ с правами на структуру.
- `schema/baseline.sql` должен приехать с кодом (он в git). Перегенерировать
  снимок при необходимости: `mysqldump --no-data --skip-comments
  --skip-add-drop-table --no-tablespaces --set-gtid-purged=OFF ...` и заменить
  `CREATE TABLE ` → `CREATE TABLE IF NOT EXISTS ` (флаг `--set-gtid-purged=OFF`
  обязателен: иначе в дамп попадают `GTID_PURGED`/`SQL_LOG_BIN`, требующие
  прав SUPER).
- В MySQL DDL автокоммитится — при падении на середине миграция может
  примениться частично; раннер предупреждает об этом в сообщении об ошибке.
- Любое изменение уже существующей (легаси) таблицы — это **новая** forward-
  миграция (`create` + `ALTER`), baseline задним числом не редактируется.

## Отправка письма с заявкой

Раньше это был закомментированный блок на 200 строк в `modules/mail.php`
с паролем от почты прямо в тексте. Теперь:

- `mail/mailer.php` — функция `SendOrderMail()` рядом по смыслу с
  `SendMailToBot()` из `messages_to_telegram.php`;
- `mail/templates/order.php` — HTML-шаблон письма;
- настройки в `config.local.php`:

```php
'mail' => [
    'enabled'    => true,
    'host'       => 'smtp.beget.com',
    'port'       => 465,
    'encryption' => 'ssl',   // 'ssl' (465), 'tls' (587) или '' без шифрования
    'username'   => 'sale@pcmarket.uz',
    'password'   => '...',
    'from'       => 'sale@pcmarket.uz',
    'from_name'  => 'Конфигуратор pcmarket.uz',
    'to'         => 'sale@pcmarket.uz',
    'subject'    => 'Конфигурация',
    'debug'      => false,   // подробный лог SMTP в error_log
],
```

Письмо уходит менеджеру (`mail.to`) и клиенту, если он оставил корректный
адрес. Это дополнение к Telegram: если SMTP недоступен, `SendOrderMail()`
пишет в лог и возвращает false — клиент всё равно видит «Заявка принята»,
а уведомление уже ушло в бота. При `enabled = false` почта не трогается.

**PHPMailerAutoload.php больше не подключается.** Библиотека 5.2.13
объявляет в нём `__autoload()`, удалённую в PHP 8.0, и на боевом PHP 8.2
это уронило бы каждую заявку фаталом. Классы грузятся напрямую
(`class.phpmailer.php` + `class.smtp.php`) — сама библиотека на 8.4
работает, проверено.

**Пароль от почты сменить.** `7UR%QHGy` лежал открытым текстом в
`modules/mail.php` и остаётся в git-истории.

**Подвал письма переписан.** В шаблоне были остатки чужой вёрстки:
ссылки на сайт `pribylwm.ru` и его соцсети (VK «wpzarabotok», Twitter
@pribylwm, посторонний YouTube-канал), логотип со старого dev-домена

## Переключатель reCAPTCHA

В `config.local.php`:

```php
'recaptcha' => [
    'enabled' => false,   // true — капча включена
    'secret'  => '...',
    'sitekey' => '...',
],
'login' => [
    'max_attempts'  => 5,
    'block_seconds' => 900,
],
```

При `enabled = false` форма входа рендерится без виджета, скрипт Google
не подключается, `modules/auth.php` не обращается к API проверки.

**Что защищает вход, пока капча выключена.** Только ограничение попыток.
Оно переведено с сессии на IP: сессионный счётчик обходился тем, что
клиент просто не присылал cookie. Данные лежат в
`storage/login_attempts.json`, IP хранится в виде SHA-256. После
`max_attempts` неудач с одного адреса вход блокируется на
`block_seconds` — включая попытки с верным паролем. Успешный вход
счётчик обнуляет.

Два предостережения:

- Режим временный. Форма входа доступна из интернета, и без капчи её
  защищает один счётчик — включите капчу обратно, как только будут
  актуальные ключи.
- Счётчик считает по `REMOTE_ADDR`. Если перед сайтом появится
  Cloudflare или другой прокси, все посетители придут с одного адреса и
  блокировка начнёт задевать всех — тогда нужно будет читать
  `X-Forwarded-For` с доверенным списком прокси.

Каталог `storage/` создаётся автоматически и закрыт своим `.htaccess`;
корневой `.htaccess` дополнительно блокирует `*.json`. Проверить оба
запрета можно только на Apache.

## Важно про антивирус на хостинге

Windows Defender при разработке пометил `security.php` как
`Backdoor:PHP/Masqshell.E` — ложное срабатывание на связку
`imagecreatefromstring(file_get_contents(...))`, которая входит в
сигнатуры «шеллов, замаскированных под картинку». Код переписан на
типовые `imagecreatefromjpeg/png/gif`, срабатывание ушло.

Это стоит иметь в виду: ImunifyAV / ClamAV на cPanel используют похожие
сигнатуры, а `security.php` подключается из каждой точки входа — его
карантин уронил бы весь сайт. Если после выкладки сайт отдаёт 500,
первым делом смотреть карантин антивируса в панели хостинга.

## Починено сверх патча безопасности

**WYSIWYG-редактор в админке.** `admin/pages/scripts.php` подключает
CKEditor **5**, а `add_constructor.php` и `modalEditSborka.php` вызывали
API CKEditor **4** (`CKEDITOR.replace`) — отсюда `CKEDITOR is not defined`
и мёртвый редактор. Попутно вскрылось, что `id="editor"` присутствовал на
странице дважды (textarea формы и div модалки, модалки подключаются на
каждой странице), а в модалке вызов вообще указывал на div-обёртку,
а не на textarea.

Переведено на API пятой версии, селекторы сделаны однозначными, дубль
`id` убран. Формы уходят через `new FormData(this)`, поэтому textarea
синхронизируется на каждое изменение в редакторе — иначе описание
уходило бы пустым.

**Разъезжалась строка товара в конфигураторе.** `.product-block` занимал
всю ширину строки, а `.price-block` лежал поверх через
`position: absolute` — длинные названия заезжали под цену. Строка
переведена на flex: название тянется и переносится, цена держит свою
колонку. Правка внесена и в `configurator/css/style.css`, и в источник
`configurator/scss/style.scss`, чтобы не потерялась при пересборке SCSS.

**Отладочный `alert('befin')`** убран из обработчика сохранения сборки
в `admin/js/admin.js` — он выскакивал при каждом редактировании.

## Что осталось незакрытым (сознательно)

- **CSRF-токенов нет.** Вместо них cookie сессии помечена `SameSite=Lax`,
  что закрывает CSRF на POST из чужого домена. Нормальные токены —
  в laravel-версии.
- **История git хранит старые секреты и дампы базы.** Чистка истории
  (`git filter-repo`) переписывает все коммиты; смена секретов из п.1
  решает проблему надёжнее.
- ~~**Роли пользователей.** Пользователь по-прежнему один и без ролей.~~
  Реализовано: полноценный RBAC (таблицы `roles`/`permissions`/
  `role_permissions`/`user_roles`, гейты `require_capability()` на всех
  admin-эндпоинтах, управление пользователями и ролями в админке). Ставится
  миграциями — см. раздел «Миграции базы данных».
- **Таблица `online`** (200k+ строк) не чистится; функция `on_line()`
  нигде не вызывается.
- **1291 висячая связь в `tree_prod`** и 4 в `tree_filter` — ссылаются на
  давно удалённые товары и фильтры.Следствие того, что старый
  `deleteProduct.php` удалял товар, не трогая связи. На витрину они не
  попадают (отсекаются JOIN-ом), поэтому чистку отложил до миграции
  структуры базы, где всё равно появятся внешние ключи.
- **Проверка `.htaccess`.** Встроенный сервер PHP её не читает, поэтому
  запрет на `settings.ini`, `config.local.php`, `*.sql` и `DEPLOY.md`
  проверяется только на Apache — пункты чек-листа выше.
- **Вход через форму логина целиком** не прогонялся: reCAPTCHA требует
  живых ключей Google. Проверены отдельно логика пароля (включая переезд
  на bcrypt) и работа админки под сессией.
